Part 1

Introduction

What CSK is, why it exists, and how to set up your environment

01 · What is CSK?

Claude Starter Kit is a learning framework that teaches developers how to work effectively with Claude Code. It provides:

  • Skills — Reusable workflow templates that guide Claude through specific tasks
  • Exercises — 6 hands-on exercises with progress tracking (~2.5 hours)
  • Tools — CLI commands for setup, verification, and testing
  • Workshop materials — This kompendium, slides, and a printable handout

Key Components

ComponentPurpose
.claude/skills/15 skill files that guide Claude through workflows
.claude/agents/Agent profiles for team collaboration patterns
exercises/6 markdown exercise files with instructions
workshop/Kompendium, slides, and handout HTML files
CLAUDE.mdProject instructions — the "bible" for Claude
Stack-agnostic. CSK works with any tech stack — React, Python, Go, Rust, whatever. The workflows and skills are language-independent.

02 · Why it exists

Developers new to AI-assisted coding often struggle with:

  • Unclear prompts — Vague instructions lead to vague results
  • No workflow — Ad-hoc requests without structure
  • Feature creep — Starting without clear requirements
  • Testing gaps — Code without tests or broken tests

What CSK solves

ProblemSolution
"I don't know where to start"/onboarding checks environment and guides setup
"My requirements are unclear"/grill-me asks Socratic questions until concept is crystal clear
"Claude adds too many features"/mockup-to-story creates scoped user stories from wireframes
"Git workflow is messy"/feature-branch enforces clean branch discipline
"Tests are an afterthought"/tdd forces test-first development
Workflow over tools. CSK isn't about learning Claude Code features — it's about learning workflows that produce quality software.

03 · Setup & workspace

Cloning the repository

CSK can be hosted on any Git provider. Choose your platform:

GitHub

# HTTPS (prompts for credentials)
git clone https://github.com/your-org/claude-starter-kit.git

# SSH (requires SSH key setup)
git clone git@github.com:your-org/claude-starter-kit.git

HTTPS with Authentication

# Clone with username (prompts for password/token)
git clone https://github.com/YOUR-ORG/YOUR-REPO.git

# When prompted for password, use your personal access token (not your login password)
# Generate token at: GitHub → Settings → Developer Settings → Personal Access Tokens

GitLab / Bitbucket / Self-hosted

# Same pattern — HTTPS or SSH
git clone https://gitlab.com/your-org/repo.git
git clone git@bitbucket.org:your-org/repo.git
Credential caching: To avoid re-entering credentials: 
# Cache for 1 hour
git config --global credential.helper 'cache --timeout=3600'

# Or store permanently (macOS keychain / Windows credential manager)
git config --global credential.helper store

04 · Model selection

Claude Code supports multiple models. Choosing the right one saves time and money.

When to use which

TaskModelWhy
Pattern replicationSonnetFast, follows existing code patterns
Writing testsSonnetUsually straightforward
Refactoring with clear scopeSonnetMechanical, bounded task
Architecture decisionsOpusNeeds trade-off analysis
Security-critical codeOpusHigh consequence of errors
Sonnet failed twiceOpusProblem harder than expected

How to switch

/model sonnet    # Fast, routine work
/model opus      # Deeper reasoning
/model haiku     # Fastest, simplest
/model           # Show options

Rule of thumb

Start with Sonnet. Switch to Opus when:

  • High consequence of errors
  • Trade-off analysis needed
  • Sonnet already failed twice
Switch mid-session. Context is preserved. No need to restart.

06 · Rules & conventions

Rules files in .claude/rules/ define project conventions that Claude follows automatically.

Two Types of Rules

TypeWhen LoadedUse For
Global rulesAlways (session start)Project-wide conventions
Path-activatedWhen working in matching pathsDomain-specific rules

Path-Activated Rules (Frontmatter)

Add frontmatter to activate rules only when working in specific directories:

# .claude/rules/e2e-testing.md
---
path: e2e-test/**
---

# E2E Testing Rules

## Test Structure
- Use `test.describe` for grouping
- One assertion per test
- Always clean up test data

## Selectors
- Prefer data-testid over CSS classes
- Never use nth-child selectors

## Timeouts
- Max 10 seconds for any wait
- Use explicit waits, not sleep
Path matching: Uses glob patterns. src/api/** matches all files in src/api and subdirectories. Rules without path: frontmatter load globally.

Common Rule Categories

FilePathContents
coding-patterns.md(global)Code style, naming conventions
testing.md**/*.test.tsUnit test patterns
e2e-testing.mde2e-test/**Playwright conventions
api-design.mdsrc/api/**REST API patterns
security.md**/auth/**Security requirements
migrations.mdprisma/**Database migration rules

Example: Global Rule

# .claude/rules/coding-patterns.md
# (no frontmatter = always loaded)

## Naming
- camelCase for variables/functions
- PascalCase for classes/components
- SCREAMING_SNAKE_CASE for constants

## Don't
- Don't use `any` type
- Don't commit console.log
- Don't use magic numbers

How Rules are Loaded

  • Session start: All rules without path: frontmatter
  • On file access: Rules matching current file path
  • Cumulative: Multiple rules can match simultaneously
  • Context cost: Keep rules concise — they consume tokens

Best Practices

DoDon't
Use path-activation for domain-specific rulesPut everything in global rules
Keep rules actionable and specificWrite vague guidelines
Include examples with rulesOnly describe what not to do
Update rules when you find new issuesLet rules become stale
Rules vs Skills: Rules are passive (always-on context). Skills are active (triggered by /command). Use rules for "always do X", use skills for "how to do Y".

08 · Context management

Claude's context window is finite. Managing it well improves quality and reduces cost.

Context Window Basics

ModelContext WindowNotes
Claude Opus 4.x200K tokens~150K words
Claude Sonnet 4.x200K tokensSame size, faster

Signs of Context Overflow

  • Claude forgets earlier instructions
  • Repeats the same suggestions
  • Loses track of file changes
  • Responses become generic

Context Commands

CommandEffectWhen to Use

/compactSummarize and compressLong session, keep working

Four phases that take you from idea to merged code

09 · The Work-Loop

Four phases that take you from idea to merged code. Each phase has a dedicated skill and produces artifacts that the next phase consumes.

flowchart LR
    P["/planning"] --> E["/execution"]
    E --> R["/reviewing"]
    R --> I["/integration"]
    R -->|NEEDS_FIXES| E
    I --> Done["✅ Merged"]
    style P fill:#0e7490,stroke:#06b6d4,color:#fff
    style E fill:#15803d,stroke:#22c55e,color:#fff
    style R fill:#a16207,stroke:#eab308,color:#fff
    style I fill:#7e22ce,stroke:#a855f7,color:#fff
    style Done fill:#15803d,stroke:#22c55e,color:#fff
PhaseSkillPurposeOutput
1. Planning/planningAnalyze, create task listplan.md, progress.md
2. Execution/executionTDD implementationCode + commits
3. Reviewing/reviewingReview against ACsAPPROVED / NEEDS_FIXES
4. Integration/integrationPR, merge, closeMerged PR
Idempotent. The loop can restart from any point. If review finds issues, execution resumes. Progress is tracked in progress.md.

10 · /planning

Analyze the codebase, understand requirements, write a task list so precise that execution never needs to make a design decision. No code in this phase!

Steps

StepActionOutput
1. Load contextRead issue, find ACsUnderstanding of requirements
2. Analyze codeFind files to changeList of affected files
3. Write plan/planningdocs/plans/{issue}-plan.md
4. Write progress(same skill)docs/plans/{issue}-progress.md

Output files

docs/plans/
├── feature-dark-mode-plan.md     # Task list with verify commands
└── feature-dark-mode-progress.md # Status: IN_PROGRESS
Rule: No code written in this phase! Planning only.

11 · /execution

Implement tasks one by one from the plan using TDD. Every task gets evidence.

        Tests->>Claude: ❌ Fails (expected)
        Claude->>Files: Implement feature
        Tests->>Claude: ✅ Passes

🔴 RED (failing test) → 🟢 GREEN (make it pass) → 🔵 REFACTOR (clean up)

14 · Progress tracking

When you close a terminal, your context is gone. progress.md is the workaround — a file that captures where you are so you can resume later.

Example progress.md

# Progress: Feature-123 Login Form

## Status
IN_PROGRESS

## Tasks
- [x] Create LoginForm component
- [x] Add form validation (Zod schema)
- [ ] Connect to auth API        ← NEXT
- [ ] Add error handling
- [ ] Write integration tests

## Decisions
- Using Zod over yup (team standard)
- Form state via react-hook-form

## Next action
Implement `useLogin` hook in `src/hooks/useLogin.ts`

How to use it

WhenAction
Starting a featureCreate docs/plans/{name}-progress.md
Completing a stepCheck off the task, update "Next action"
Resuming after break"Read progress.md and continue"
FinishingSet Status to DONE
progress.md is your external memory. Claude can't remember across sessions, but it can read files.

17 · /tdd

TDD (Test-Driven Development) is a discipline: write the test before the implementation.

The cycle

flowchart LR
    R["🔴 RED
Write failing test"] --> G["🟢 GREEN
Make it pass"]
    G --> RF["🔵 REFACTOR
Improve code"]
    RF --> R

Example

// Step 1: RED — Write failing test
describe('add', () => {
  it('should add two numbers', () => {
    expect(add(2, 3)).toBe(5);
  });
});

// Step 2: GREEN — Minimum code to pass
function add(a, b) {
  return a + b;
}

// Step 3: REFACTOR — Improve without breaking tests
Don't write implementation first. If you write code before tests, you'll write tests that pass — not tests that verify correct behavior.

18 · /grill-me

The grill-me skill uses Socratic questioning to force clarity on your project idea.

Question flow

  1. Problem: "What specific problem are you solving?"
  2. Users: "Who specifically will use this?"
  3. Differentiator: "Why won't they just use [existing solution]?"
  4. Core: "What's the ONE thing this must do well?"
  5. Non-goals: "What's explicitly NOT in version 1?"
Don't defend — refine. Each question helps you find holes in your thinking.

23 · Code review

PR checklist (author)

  • ☐ Self-reviewed the diff
  • ☐ Tests pass locally
  • ☐ No debug code (console.log, TODO)
  • ☐ Follows project conventions
  • ☐ PR description explains the change

Good review comments

// ✅ Constructive
"Consider extracting this into a helper function
for reusability."

// ✅ Specific with solution
"This could throw if `user` is null. Add a guard:
if (!user) return null;"

// ✅ Questioning (not demanding)
"Why did you choose X over Y here?"
Reviews improve everyone. Approach them as collaborative learning.

25 · Git worktrees

Work on multiple features in parallel without stashing or switching branches.

What is a Worktree?

A worktree is a separate working directory linked to the same repository. Each worktree has its own branch.

# Start Claude with automatic worktree creation
claude --worktree feature-b

# Claude creates .worktrees/feature-b/ and starts there
# Now you have two directories:
# ./                        (main repo)
# .worktrees/feature-b/     (isolated workspace)
Worktrees + CI Overlap = productivity. Never wait for CI. Start the next feature while tests run.

28 · Agent Teams — Parallel & Specialized Work

Spawn subagents for parallel tasks or specialized roles. Each agent runs with its own context window.

When to Use Agents

ScenarioExample
Parallel workReview 5 files simultaneously
SpecializationSecurity audit, QA testing, documentation
Fresh contextAvoid polluting main conversation

Agents + Work-Loop Integration

Different agents can own different phases:

# Main agent: coordinates the work
You: "Plan authentication feature"
Claude: *runs /planning, creates task list*

# Spawn specialized agent for execution
You: "Spawn Tom to implement the login form"
Claude: *spawns subagent with task context*

# Spawn QA agent for review
You: "Spawn Scott to review the auth code for security issues"
Claude: *spawns code-reviewer subagent*

# Spawn DevOps agent for deployment
You: "Spawn Dan to set up CI pipeline for auth tests"

Agent Profiles

Define specialized agents in .claude/agents/:

AgentFocusProfile
TomFull-stack development.claude/agents/tom.md

AkselArchitecture review.claude/agents/aksel.md
DanDevOps / CI/CD.claude/agents/dan.md

How to Spawn Agents

# Simple spawn
"Spawn a code-reviewer agent to check auth.ts"

# Spawn with specific focus
"Spawn a security agent to audit the payment flow for OWASP issues"

# Spawn multiple in parallel
"Spawn 3 agents: one for API review, one for frontend, one for tests"

# Spawn with worktree isolation
"Spawn Tom in a worktree to implement feature-x while I work on feature-y"
Critical: Subagents don't see your conversation history. Brief them with ALL context they need — files, goals, constraints. Think of it like onboarding a new team member.

Anti-patterns

Don'tDo
"Review the code" (no context)"Review auth.ts for SQL injection, check line 45-80"
Spawn for simple tasksUse agents for 10+ minute tasks
Forget to collect resultsAlways ask agent for summary before dismissing

37 · The Non-Determinism Problem

To work effectively with Claude, you must understand one fundamental truth: LLMs are probabilistic, not deterministic. This explains why Claude sometimes ignores instructions, why outputs vary between runs, and why guardrails exist throughout this entire framework.

Industry data (2026): AI-generated code contains roughly 1.7× more defects than human-written code. AI code generation increases velocity by 25-35%, but creates a quality gap as code volume outstrips human review capacity. — New Relic State of AI Coding 2026

Harness Engineering: The Solution

The industry term for solving this is Harness Engineering — building the deterministic runtime layer that wraps an LLM. As Martin Fowler writes:

"LLM compliance with instructions is probabilistic, not deterministic. They must be combined with deterministic outer-harness constraints, such as linters and CI gates, to be reliable at scale."

The key insight: Telling an agent "follow coding standards" in a prompt is fundamentally different from wiring a linter that blocks the PR when standards are violated. The first relies on probabilistic compliance; the second enforces deterministic constraints.

Proof it works: LangChain's case study showed harness-only changes moved their coding agent from rank 30 → top 5 on Terminal Bench 2.0 with no model swap. "Harness design is the primary performance lever, not model capability."

Mental Model: Image Generation for Code

Think of Claude like Midjourney for images. You describe intent ("A sunset over mountains"), and you get varying outputs. Different runs produce different images. Fewer constraints = more variation.

Same with code. You describe a feature, Claude generates implementation. Different runs might produce different designs. Without guardrails, you might get:

  • Inconsistent naming (camelCase one run, snake_case the next)
  • Different architectural approaches (class-based vs functional)
  • Hallucinated imports (functions that don't exist)
  • Forgotten acceptance criteria
  • Subtle bugs that appear only sometimes

What This Means Practically

RealityWhy
Claude ignores instructions when it "decides to"Probabilistic inference doesn't guarantee compliance
Output varies between runsSampling != determinism
Different model versions behave differentlyTraining differences, capability gaps
Hallucinations happen (imports, patterns, claims)LLMs generate plausible-sounding text
You can't trust Claude to "just do it right"Probability ≠ correctness guarantee

The Solution: Layered Guardrails

The more Claude can do, the tighter the leash must be. CSK's entire architecture is built around catching the problems that probabilistic inference creates:

LayerToolCatchesWhen
EditorTypeScript strict mode, ESLintType errors, style violations, obvious mistakesImmediately after Claude writes code
Pre-commitBiome, custom hooksFormat, banned patterns, schema driftBefore commit to git
Pre-pushUnit tests, type-check, compilationBroken builds, logic errors, regressionsBefore pushing to remote
CI PipelineFull test suite, E2E tests, lintersSubtle bugs, integration failures, regressionsBefore merge
Code ReviewHuman eyes (not AI)Subtle AI-introduced bugs, missed ACs, security issuesBefore production

Why Each Layer Matters

Editor layer: Catches the obvious — typos, missing imports, type errors. Fast feedback loop. Claude sees red squiggles and can fix immediately.
Pre-commit layer: Prevents bad commits. Format consistency, no debug code, no secrets. Stops bad code from reaching git history.
Pre-push layer: Unit tests verify logic. Type-check verifies interface contracts. Compilation verifies structure. Catches logic errors BEFORE CI.
CI layer: Full integration test suite. E2E tests. Catches bugs that only appear in realistic contexts (race conditions, timing, state interaction).
Code review layer: The guardrail of last resort. Humans catch the subtle bugs: missed acceptance criteria, security issues, architectural mismatches. This is why code review is NOT optional.

The Rule: The More Claude Can Do, The Tighter The Leash

Capability LevelTask ScopeRequired Guardrails
NarrowSingle file, single functionESLint, unit tests
MediumFeature across multiple files+ Pre-commit hooks, type-check, integration tests
BroadFull feature from idea to release+ E2E tests, CI pipeline, human code review
AutonomousBatch task execution without supervision+ Video recordings, acceptance criteria tests, monitoring

Harden Over Time

Every bad behavior Claude exhibits → add a guardrail. Every time a bug slips through → tighten the layer that missed it.

Example: Claude keeps forgetting to validate user input
→ Add Zod validation to error checklist
→ Add ESLint rule for unvalidated params
→ Add unit test template for all endpoints
→ Next time Claude forgets → caught immediately

Acceptance Criteria Must Be Testable

For this system to work, every acceptance criterion must have a corresponding test:

  • ❌ Untestable: "The form should work well"
  • ✅ Testable: "Submitting valid data returns 200 and saves to database"
  • ✅ Testable: "Submitting invalid email shows error message"
  • ✅ Testable: "Loading takes <500ms (measured with Lighthouse)"

Use video recordings for before/after comparison of visual features.

The Core Principle

You cannot trust Claude to produce correct code without verification.

This is not a flaw of Claude. It's the nature of probabilistic AI. The answer is not to hope for better — it's to build layers of verification that make correctness inevitable.

Why This Matters for Your Team

  • No "we'll fix it later." Every layer catches bugs that would cost money or customer trust to fix in production.
  • No single-point failures. If one layer fails, the next one catches it. Redundancy is intentional.
  • No false confidence. A test passing is not proof of correctness. A PR approved is not proof of correctness. Only a deployed feature used by real customers is proof.
  • Automate ruthlessly. If a check is important, automate it. Pre-commit hooks, CI gates, linters. Make correctness the path of least resistance.
The good news: Once these layers are in place, you can work fast. Claude can write more code, take more risks, explore more solutions. The guardrails catch the problems.
