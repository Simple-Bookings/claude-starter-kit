Part 1 · Intro

What is Claude Code?

Anthropic's official CLI for AI-assisted software development — an intelligent pair programmer that reads, writes, and executes code.

What it CAN do

  • Read and understand your entire codebase
  • Write, edit, and refactor code across files
  • Run shell commands (git, npm, tests)
  • Search the web for documentation
  • Create and review pull requests
  • Debug failing tests with context

What it WON'T do

  • Replace human judgment on design
  • Understand your business domain magically
  • Execute destructive commands without asking
  • Remember context between sessions

It's a tool, not a replacement. You're still the architect.

Part 2 · Foundation

🧠 Model Selection

Different tasks need different models. Default is Sonnet — switch to Opus when needed.

Task Model Why
Pattern replication sonnet Fast, follows existing patterns
Writing tests sonnet Usually straightforward
Refactoring sonnet Mechanical, bounded scope
Architecture decisions opus Needs trade-off analysis
Security-critical code opus High consequence of errors
Sonnet failed twice opus Problem harder than expected 
/model sonnet    # Fast, cheap (default)
/model opus      # Slower, deeper reasoning

Strategy Savings How

Part 3 · Work-Loop

The 4 Phases

Four phases that take you from idea to merged code. Each phase has a dedicated skill. 

flowchart LR
    P["/planning"] --> E["/execution"]
    E --> R["/reviewing"]
    R --> I["/integration"]
    R -->|NEEDS_FIXES| E
    I --> Done["✅ Merged"]
    style P fill:#ecfeff,stroke:#06b6d4
    style E fill:#f0fdf4,stroke:#22c55e
    style R fill:#fefce8,stroke:#eab308
    style I fill:#faf5ff,stroke:#a855f7
    style Done fill:#f0fdf4,stroke:#22c55e

Key insight: Each phase produces artifacts that the next phase consumes. The loop is idempotent — you can restart from any point.

Part 3 · Work-Loop

Work-loop 1/4 — /planning

Analyze the codebase, understand requirements, write a task list so precise that execution never needs to make a design decision. 

sequenceDiagram
    autonumber
    participant Dev
    participant Claude as Claude Code
    participant Files as Filesystem
    Dev->>Claude: /planning "add dark mode"
    Claude->>Files: Read CLAUDE.md, existing components
    Claude->>Files: Analyze current styling patterns
    Claude->>Files: Write docs/plans/feature-plan.md
    Claude->>Dev: Task list with file paths + verify commands

Output: plan.md with concrete tasks, each with file path and verification command

Rule: No code written! Planning only. Read-only exploration.

Part 3 · Work-Loop

Work-loop 2/4 — /execution

Implement tasks one at a time from the plan. Each task = one iteration. Test-Driven Development by default. 

sequenceDiagram
    autonumber
    participant Dev
    participant Claude as Claude Code
    participant Files as Filesystem
    participant Tests as Test Runner
    loop For each task in plan
        Claude->>Files: Read task from plan.md
        Claude->>Files: Write failing test first
        Tests->>Claude: ❌ Test fails (expected)
        Claude->>Files: Implement feature
        Tests->>Claude: ✅ Test passes
        Claude->>Files: Update progress.md
    end

TDD cycle: Red (write failing test) → Green (make it pass) → Refactor. Never skip the red phase.

Part 3 · Work-Loop

Work-loop 3/4 — /reviewing

Self-review against acceptance criteria. Output is APPROVED or NEEDS_FIXES.

Review Checklist

  • All acceptance criteria met?
  • Tests exist and pass?
  • No debug code (console.log)?
  • Follows project conventions?
  • No security vulnerabilities?
  • Build still works?

Outcomes

APPROVED

→ proceed to /integration

NEEDS_FIXES

→ loop back to /execution

Part 3 · Work-Loop

Work-loop 4/4 — /integration

Create PR, handle CI, get it merged. Cleanup branches. 

sequenceDiagram
    autonumber
    participant Dev
    participant Claude as Claude Code
    participant Git as Git/GitHub
    participant CI as CI Pipeline
    Claude->>Git: git add -p (selective staging)
    Claude->>Git: git commit -m "feat: ..."
    Claude->>Git: git push origin feature/xxx
    Claude->>Git: gh pr create --base develop
    Git->>CI: Trigger CI checks
    CI->>Git: ✅ All checks pass
    Dev->>Git: Approve and merge PR
    Claude->>Git: git branch -d feature/xxx

Done: Feature merged to develop, branch cleaned up, progress.md marked complete.

Part 3 · Work-Loop

📝 Progress Tracking — Your External Memory

Claude doesn't remember between sessions. progress.md is the workaround. 

# Progress: Feature Login

## Status
IN_PROGRESS

## Tasks
- [x] Create LoginForm
- [x] Add Zod validation
- [ ] Connect to auth API  ← NEXT
- [ ] Add error handling
- [ ] Write tests

## Next action
Implement useLogin hook

How to Use

  • Starting: Create progress.md
  • Each step: Check off task, update "Next"
  • Resuming: "Read progress.md and continue"
  • Done: Set Status to DONE

Key insight: progress.md is your external memory. Claude can't remember across sessions, but it can read files.

Recap

What we learned: The Work-Loop

Key Concepts

  • Planning = no code, only analysis and task list
  • Execution = TDD: RED → GREEN → REFACTOR
  • Reviewing = self-review against acceptance criteria
  • Integration = PR, CI, merge, cleanup
  • NEEDS_FIXES loops are normal, not failures

Remember

  • NEVER skip the RED phase in TDD
  • Each phase produces artifacts for next phase
  • Loop is idempotent — restart from any point
  • Verify phase outputs before moving forward
  • Review founds bugs — always do it

Part 5 · Supporting

🔥 /grill-me — Clarify Before You Build

Socratic questioning until your concept is crystal clear. Run BEFORE /planning.

Questions You'll Face

  • Problem: What specific problem are you solving?
  • Users: Who specifically will use this?
  • Differentiator: Why not use existing solutions?
  • Core: What's the ONE thing it must do well?
  • Non-goals: What's explicitly NOT in v1?
  • Data: What data do you need to store?

Output

## Concept: TimeTracker
**Problem:** Freelancers lose billable
  hours because they forget to track

**Core feature:** One-click timer

**Non-goals:**
- Invoicing (v2)
- Team features (v2)
- Mobile app (v2)

Don't defend — refine. Each pushback helps find holes in your thinking before you write code.

Part 5 · Supporting

🧪 /tdd — Test-Driven Development

Write the test first. Make it fail. Then make it pass. No exceptions. 

flowchart LR
    R["🔴 RED
Write failing test"] --> G["🟢 GREEN
Make it pass"]
    G --> RF["🔵 REFACTOR
Clean up"]
    RF --> R
    style R fill:#fef2f2,stroke:#ef4444
    style G fill:#f0fdf4,stroke:#22c55e
    style RF fill:#eff6ff,stroke:#3b82f6

❌ Never skip RED: A test that never failed might pass by accident. Always see it fail first.

✅ Minimal GREEN: Write the simplest code that makes the test pass. Refactor after.

Part 6 · Advanced

🌲 Git Worktrees — Parallel Development

Work on multiple features without stashing. Each worktree is an independent checkout. 

# Terminal 1: Start Claude with worktree for feature-a
claude --worktree feature-a
# Claude opretter .worktrees/feature-a og starter dér
/planning "implement feature A"

# Terminal 2: Start Claude with worktree for feature-b
claude --worktree feature-b
# Claude opretter .worktrees/feature-b og starter dér
/planning "implement feature B"

CI Overlap: While CI runs on feature-a, start planning feature-b. A 10-minute CI run = 2-3 planning cycles.

🤖 Agent Teams — Parallel & Specialized Work

Spawn subagents for parallel tasks or specialized roles. Each agent has its own context.

When to Use Agents

  • Parallel work: Review 5 files at once
  • Specialization: Security audit, QA, docs
  • Fresh context: Avoid pollution
  • CI wait: Plan next while CI runs

Agents + Work-Loop

  • /planning: Main agent plans
  • /execution: Spawn Tom for coding
  • /reviewing: Spawn Scott for QA
  • /integration: Spawn Dan for deploy
# Spawn a subagent for code review
"Spawn a code-reviewer agent to check auth.ts for security issues"

# Spawn multiple agents in parallel
"Spawn 3 agents: one to review API, one for frontend, one for tests"

# Agent profiles in .claude/agents/
.claude/agents/scott.md    # QA focus, testing patterns
.claude/agents/quinn.md    # Security focus, OWASP rules

Remember: Subagents don't see your conversation. Brief them like a new colleague!

Part 6 · Advanced

🎲 The Non-Determinism Problem

LLMs are probabilistic, not deterministic. Output varies. Claude sometimes ignores instructions.

The Reality

  • AI code has 1.7× more defects
  • Output varies between runs
  • Instructions are probabilistic
  • Hallucinations happen

The Solution: Guardrails

  • Editor: TypeScript, ESLint
  • Pre-commit: Biome, hooks
  • CI: Full test suite
  • Review: Human eyes

Key insight: "Follow coding standards" in a prompt ≠ a linter that blocks the PR. The more Claude can do, the tighter the leash.

Part 7 · Reference

🔧 When Things Go Wrong

Common problems and how to fix them. (Spoiler: most have simple solutions.)

📦 Context Overflow

Symptom: Claude suddenly forgets what you discussed earlier.

Fix: Run /clear or /compact to compress context. Start a fresh session if needed.

🤔 Claude Hallucinates

Symptom: Claude references files or functions that don't exist.

Fix: Always verify with grep or file read before acting. "Trust but verify" — don't blindly accept Claude's claims.

🧪 Tests Fail in CI but Pass Locally

Symptom: Test passes in terminal but fails in GitHub Actions.

Fix: CI environment differs (database, caching, parallel execution). Download CI logs, check for timing issues or race conditions. Add explicit waits or dependencies.

📋 Planning Missed the Mark

Symptom: Plan looked good, but midway through execution it's wrong.

Fix: Go back to planning. Refine the plan, verify file paths are correct, check if requirements changed. A bad plan found early saves hours.

🚫 Claude Refuses to Execute

Symptom: "I can't do that" / "I don't have permission."

Fix: Check if command is destructive (git reset --hard). If allowed, be explicit: "Run this command: X". If truly blocked, use a safe alternative.

Golden rule: When stuck, trace back to the previous stable point. Review Claude's logic. Verify assumptions. Root cause beats quick fixes.
